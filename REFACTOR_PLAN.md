# SemNetCleaner Refactor — Tracking Document

Full rebuild of `SemNetCleaner` (originally CRAN v1.3.7) in this sibling directory. The
original, untouched source lives at `../SemNetCleaner` — read-only reference, never edited.

**Goal:** single-responsibility functions, input validated/coerced up front, bugs
eliminated, the ~80-85% fluency/free duplication collapsed, the interactive wizard made
genuinely unit-testable for the first time, structural conventions matched to `../SemNeT`'s
own rebuild.

**Full plan file:** `/home/alextops/.claude/plans/please-take-a-look-elegant-axolotl.md`
(context, rationale, and the binding decisions below were made there).

**Execution cadence:** one phase at a time. Finish a phase, run its verification, update
this file's status table, check in before starting the next phase.

## Binding decisions (already made, do not re-litigate)

1. **Copy first.** This directory is a real, literal copy of the original package tree
   (frozen as this repo's first commit); `../SemNetCleaner` is never touched.
2. **Merge the ~80%-duplicated fluency/free pairs** into one parameterized engine each:
   `auto.spellcheck`/`.free` → `auto_spellcheck(type = ...)`; `spellcheck.dictionary`/`.free`
   → `spellcheck_dictionary(type = ...)`; `textcleaner.fluency`/`.free`'s shared scaffolding
   → one internal core under `textcleaner()`; `prep.spellcheck.dictionary`'s internal
   fluency/free branches → one shared parameterized core. **Exception:**
   `correct.data`/`correct.data.free` stay separate (genuinely different algorithms — the
   free variant does cue/ID sequence row-splicing fluency doesn't need).
3. **Every interactive/prompting function takes an injectable input-reader** (defaults to
   real `readline()`/`menu()`), built once as `read_input()` in `R/helpers.R` (Phase 1), so
   the whole wizard can be driven by a scripted queue of answers in tests.
4. **`inst/Automated/app.R` (the Shiny companion GUI) is deferred entirely** — its two known
   bugs (hardcoded `sep = "\\"` temp-path join at line 117, `<<-` global leak in `onStop()`
   at line 210) are recorded, not fixed, this cycle. `AutomatedEdit()` becomes a thin
   `requireNamespace()`-guarded stub; `correct_changes()`'s console-editor (`edit()`) path
   stays fully in scope.
5. **`convert2snafu()` drops `easycsv` entirely**, takes an explicit `path =` argument
   instead of `easycsv::choose_dir()`.
6. **Full backward compatibility** via `R/legacy.R`: every pre-2.0.0 exported dotted name
   keeps working (`bad.response`, `best.guess`, `bin2resp`, `convert2snafu`, `pluralize`,
   `qwerty.dist`, `read.data`, `resp2bin`, `singularize`, `textcleaner`).
7. **Naming**: `resp2bin` → `responses_to_binary`, `bin2resp` → `binary_to_responses`
   (reusing `SemNeT`'s own already-established names for the identical concept);
   `qwerty.dist` → `qwerty_distance`; `bad.response` → `bad_response`; `best.guess` →
   `best_guess`; `read.data` → `read_data`. `textcleaner` and `convert2snafu` are **kept
   unchanged** (flagship/branding name, and an established `convert2<external-tool>`
   pattern matching `SemNeT`'s own `convert2igraph`/`convert2cytoscape` precedent,
   respectively) — neither needs a `legacy.R` wrapper.
8. **Testing.** Zero tests existed in the original. Every new/merged function gets
   `tests/testthat/test-<name>.R`, built against the bundled fixtures (`open.clean`,
   `open.animals`, `open.preprocess`, `letter.freq`), plus scripted-input tests for every
   interactive function.

- One file per exported function, new snake_case name, each with its own `<name>_errors()`
  validation subroutine called first.

### Phase 2 follow-up: `pluralize()`/`singularize()` rule and exception-word improvements (per request)

Per direct request, updated `pluralize()`/`singularize()`'s rules and expanded their exception
tables where possible. This is a deliberate **behavior improvement**, not a bug-compatibility
fix — the original's own dictionary-only (coca) validation had real, confirmed gaps that no
amount of faithful porting could have preserved-and-also-fixed at the same time. Every change
below was verified empirically against real dictionary data
(`SemNetDictionaries::coca.dictionary`/`hunspell.dictionary`/`general.dictionary`/
`cocaspell.dictionary`, and the real `hunspell::hunspell_check()` spell-checker), not guessed.

**Root-cause finding:** `coca.dictionary` (a corpus-frequency word list, 80,381 entries) contains
many *informal-but-attested* plural forms that are grammatically valid English but not the
idiomatically standard form for a given word — confirmed empirically: `"deers"`, `"salmons"`,
`"elks"`, `"bisons"`, `"trouts"` are all `TRUE` in `coca.dictionary`, and several even pass the
real `hunspell::hunspell_check()` spell-checker (since they *are* grammatically legal words).
No dictionary-membership check, however broad, can distinguish "grammatically valid" from
"idiomatically standard" — that requires a curated exception list. Separately, `coca.dictionary`
is also missing several correctly-spelled words the OTHER direction (`"walruses"`, `"matrices"`,
`"vertices"`, `"irises"`, `"peduncles"`, `"mallees"` are all real English but not in coca) —
`hunspell::hunspell_check()` correctly recognizes most of these as real words.

**Changes made:**

1. **`word_is_recognized()`** (new, `helpers.R`) — checks `coca.dictionary` first (fast, no
   extra dependency), then falls back to the real `hunspell::hunspell_check()` spell-checker
   when installed (`hunspell` is already an optional package-wide `Suggests` dependency, so
   this degrades gracefully to coca-only behavior when it isn't available). Used in place of a
   bare `word %in% checker` at `pluralize()`'s and `singularize()`'s **final** dictionary gates
   only — their internal per-branch candidate-refinement checks were deliberately left
   coca-only/unchanged, to keep the change's scope contained to the one true bottleneck every
   code path in both functions ultimately flows through, without risk of destabilizing already-
   verified branch-specific behavior.
2. **Irregular-table matches now bypass the dictionary gate entirely** in both `pluralize()`
   and `singularize()` (early `return()`, before any dictionary check at all) — a hand-curated
   entry may legitimately target a word not itself present in any of the checked dictionaries
   (several of the new animal names below), and re-validating it would silently discard an
   already-correct match. This is the same fix, one architectural layer up, as bugs #1/#14's
   "a correct answer gets silently discarded by an over-eager secondary check" pattern. Fixed,
   as a direct consequence, two previously-broken `singularize()` entries noted-but-left-alone
   earlier in Phase 2 (`"peduncles"`→`"peduncle"`, `"mallees"`→`"mallee"`, neither in
   `coca.dictionary`).
3. **`pluralize()`'s final fail-safe now also tries `"+es"`** (after `"+s"` fails), not just
   `"+s"` — fixes `virus`/`campus`/`bonus`/`census`/`chorus`/`circus`/`status`/`iris` and
   several Latin `-is` words *without* needing an individual table entry for each (their
   `"+es"` form was already a real, recognized word; the original simply never tried it).
4. **`irregular_plurals` (shared table, `helpers.R`) expanded** with two curated categories,
   both verified against real dictionary/spell-checker data:
   - **Invariant-plural nouns** (singular = plural), weighted toward this package's primary use
     case (verbal-fluency **animal** naming — see the bundled `open.animals` data): `deer`,
     `moose`, `sheep`, `swine`, `salmon`, `trout`, `elk`, `bison`, `fish`, `shrimp`, `buffalo`,
     `species`.
   - **Words the rule engine's own first-choice candidate systematically mishandles**: `ox` →
     `oxen` (genuine irregular); `bus` → `buses` (the naive fail-safe's `"+s"` form, `"buss"`,
     is a coincidentally real but wrong/archaic word); `walrus` → `walruses`, `matrix` →
     `matrices`, `vertex` → `vertices`, `iris` → `irises`, `hippopotamus` →
     `hippopotamuses`, `platypus` → `platypuses` (the linguistically correct target wasn't in
     any of the four dictionaries checked); `octopus` → `octopi` (finally matches what this
     function's own original documentation always claimed — previously silently rejected,
     since even `hunspell_check()` rejects "octopi" as a folk-etymology plural); `genius` →
     `geniuses` (found *during this very fix*: the rule engine's own `-us/-i` candidate,
     `"genii"`, turned out to be a real, hunspell-recognized word — just the archaic
     "guardian spirit" sense, not the modern plural for people — overridden in favor of
     the standard modern form).

**A note on scope:** invariant-plural judgment calls for `fish`/`shrimp`/`buffalo` specifically
are a **style preference**, not a strict correctness fix — `"fishes"`/`"shrimps"`/`"buffalos"`
are all independently valid English, just less common than the invariant form for a casual
verbal-fluency response. Flagging this explicitly in case the `"+s"`/`"+es"` forms are
preferred instead for any of these three.

**Verified:** all 305 tests pass (62 new — dedicated coverage for every new table entry, the
`"+es"` fallback, and the `peduncle`/`mallee` gate-bypass fix); re-ran the full original-vs-new
comparison harness (see the main Phase 2 verification method above) — `bad_response`,
`qwerty_distance`, `responses_to_binary`, `binary_to_responses`, `best_guess` (which calls
`pluralize()` internally) all still match the original exactly; `pluralize`/`singularize`
now correctly diverge from the old reference (expected — this is a deliberate improvement,
not a bug-compatibility port). Performance note: the `hunspell` fallback path (only reached

(`microbenchmark`) versus ~0.4ms for the coca-only fast path or ~16us for an irregular-table
early return — an acceptable, deliberate quality-for-speed tradeoff given it's genuinely a
fallback path, not the common case; flagged as a candidate for a future optimization pass

cost) if performance becomes a real constraint.

### Phase 3 follow-up: optimize/rework the core checks (per direct request)

Asked directly: for Phase 3's functions, optimize in place or rework through a more
efficient means? Answer given and executed: mostly optimize, with one genuine rework
(`brit_us_conversion_vector()`) and one case where profiling found a better, less invasive
fix than the rework originally proposed (`best_guess()`).

**1. Generalized the memoized-hash pattern beyond `coca.dictionary`.** New `helpers.R`
functions `get_dictionary_hash()`/`dictionary_contains()` — `multiple_words()`,
`response_splitter()`, and (transitively, via `best_guess()`) `ind_word_check()` all repeat
`word %in% full_dictionary`-style checks against whatever dictionary vector was passed in,
the same "`match()` rebuilds its hash every call" tax `coca.dictionary` had in Phase 2, just
not hardcoded to one vector. Cache keyed by `identical()` against a small (4-entry)
most-recently-used list rather than a content fingerprint — benchmarked `identical()` at
~1.7us when the same object is passed repeatedly (the common case; R short-circuits via
reference equality) and ~280us worst-case (two separately-built 80K-word vectors with
identical content), both negligible next to the ~130-220ms hash-build cost avoided.

**A real pessimization caught before shipping it**: benchmarked the memoized hash against
plain `%in%` across a range of dictionary sizes and found the hash is *not* a universal
win — `%in%`/`match()`'s own cost only becomes expensive at real scale. Measured crossover:
raw `%in%` wins below ~2,000-5,000 words (`animals.dictionary`, 1,252 words: ~3.5-6.5us raw
vs. ~12-13us hashed — the hash path's own `identical()` scan + `vapply()` overhead costs
*more* than `%in%`'s cheap rebuild at that size); the memoized hash wins decisively above
that (`coca.dictionary`, 80,381 words: ~355us raw vs. ~17us hashed). `dictionary_contains()`
now dispatches on `length(dictionary) < 3000` accordingly, so `animals.dictionary`-scale
calls stay on the fast `%in%` path while `coca.dictionary`-scale calls get the memoized win.

**2. `brit_us_conversion_vector()` reworked, not just optimized.** The original matched the
*dictionary* (780 entries) against `vec` (`match(names(brit2us), vec)`) — backwards (matching
the big side against the small side) and redundant (an equivalent `match()` re-run a second
time just for index positions). **Bug #21 found and fixed**: this backwards direction means
`match()` returns only the *first* `vec` position per dictionary entry, so a duplicated word
in `vec` had only its first occurrence converted — confirmed by direct reproduction against
the untouched original. Reworked to match `vec` against the dictionary directly (the natural
direction, one `match()` call, no redundancy) — fixes the duplicate-word bug as a side effect
of asking the right-direction question, and is ~4x faster (~60.7us -> ~16us median,
`microbenchmark`, n=300) from eliminating the redundant second `match()`.

**3. `best_guess()`: investigated the originally-proposed rework, found a better fix via
profiling instead.** The plan going in was to batch `stringdist()` calls across candidate
words. Profiling `best_guess("dogg", full_dictionary = animals.dictionary)` found the real
cost wasn't `stringdist()` at all (~1.4ms) — it was a 6-word `pluralize()` loop over candidate
words costing ~310ms of the call's ~315ms total, almost entirely attributable to ONE rare
word ("degu") failing every check and falling through to `hunspell_check()` not once but
twice (the "+s" and "+es" fallback attempts added in the earlier rule-improvement pass).
Since `word_is_recognized()` is a pure function of `word` alone, its verdict is safe to
memoize permanently per word for the life of the session — added `.word_recognition_cache`
to `helpers.R`. Confirmed ~200x faster on a repeated check of the same word (~330us -> ~1.7us)
once cached, and this compounds across a realistic session: 10 different misspelled animal
names run through `best_guess()` a second time (candidate words overlap heavily across
different misspellings of related animals) dropped from ~808ms to ~30ms, a ~27x end-to-end
speedup, all guesses verified correct both passes. No changes to `best_guess()`'s own code at
all — memoizing one layer down made the originally-proposed batching rework unnecessary.

**Verified:** all 361 tests pass (2 new, for bug #21's regression); re-ran every existing
Phase 3 `identical()`-against-original comparison — all still pass (this pass changed
performance characteristics and fixed bug #21, not behavior elsewhere).

**This phase's own review turned up a much bigger finding than expected: a systemic, previously-unnoticed R indexing gotcha (`x[-which(cond)]` on a vector, list, or matrix dimension returns the whole thing *emptied out*, not *unchanged*, whenever `which(cond)` is itself empty — R can't distinguish a "negative empty" index from a "positive empty" one; both are just `integer(0)`).** This single mechanism produced 4 of the 5 real bugs found this phase, two of them severe:

- **Bug #37:** `correct_data()`'s `apply(data, 2, function(x){ !is.na(x) })` crashes on a 1-participant dataset (`apply()` simplifies a per-column scalar result to a plain vector instead of a matrix; `rowSums()` then needs ≥2 dimensions). Fixed via `!is.na(data)` directly (already vectorized, no row-count-dependent simplification).
- **Bug #38, compounding #37:** `correct_mat[, -which(...)]` (removing all-NA columns) drops matrix-ness when exactly 1 column survives — `row.names(correct_mat) <- ...` then crashes. Fixed via `drop = FALSE`.
- **Bug #39, severe, not an edge case:** `correct_data()`'s Perseverations count — `correct_ord[-which(correct_ord == "NA")]` — was silently **always 0** whenever a participant had no literal `"NA"`-string response, i.e. the ordinary case for anyone with no bad responses. Confirmed and quantified directly against real `open.preprocess` data: the untouched original reports a total of **3** perseverations across all 516 participants; the correct total, computed identically but without this bug, is **116** — a ~38x undercount, affecting 73 of 516 participants (14%). Fixed via a positive `!=` filter.
- **Bug #40, compounding the same mechanism on a matrix's column dimension:** "Remove columns that are all NA" collapses to a *zero-column* matrix whenever every allocated response slot is actually used (nothing to remove) — confirmed the untouched original then crashes one line later at `colnames(correct_mat) <- ...` (`1:ncol(correct_mat)` reverse-ranging to `1:0` on the now-zero-width matrix — also fixed, via `seq_len()`, same class as bugs #15-17).
- **Bug #41, found by auditing every other occurrence of this same pattern across the whole already-built codebase once the mechanism was understood — the most severe of the five, and the only one in already-committed Phase 4 code:** `spellcheck_dictionary()`'s two GO-BACK-undo sites did `changes <- changes[-which(names(changes) == paste(ind[main_count - go_back_count]))]` on a **list**. Confirmed reachable: GO BACK can revert to a response resolved via SKIP or KEEP AUTO-CORRECT, neither of which ever calls `change_format()` — so `changes` has no entry for that response's index, and the resulting empty `which()` **discards every other already-recorded change for completely unrelated responses**, not just a no-op for the missing one. Fixed via a positive `!=` filter. A full end-to-end wizard reproduction proved impractical to hand-construct reliably (the `go_back_count`/`main_count` bookkeeping is intricate enough that isolating this one path from everything else it touches wasn't tractable) — covered instead by a direct regression test of the exact mechanism, same as bug #14's own (`best_guess.R`) precedent.

**Audited every other occurrence of `[-which(` in the codebase** once this mechanism was understood, confirming each is either already fixed above or genuinely safe: `qwerty_distance.R`'s `keyb[-which(duplicated(row.names(keyb))), ]` (the hardcoded keyboard-distance matrix has a real, structural duplicate row name baked in, so `which()` is never empty by construction), `convert2snafu.R`'s `name[-which(name == "list")]` (`substitute(list(...))` always deparses with `"list"` as its first element for 2+ arguments, guaranteed by R's own semantics, not data-dependent), `correct_changes.R`'s `chn_mat[, -which(apply(chn_mat, 2, function(x){ all(is.na(x)) }))]` (guarded by an enclosing `if(any(...))`, so `which()` is provably non-empty whenever this line runs), and `spellcheck_dictionary.R`'s `target[-which(target_punct == "")]` (also guarded by an enclosing `if(any(target_punct == ""))`). `best_guess.R` was already using the safe positive-filter idiom (`dictionary[dictionary != "general"]`) from Phase 2, not this pattern at all.

**Two further bugs found and fixed in `correct_changes()`, unrelated to the `-which()` family:**

- **Bug #35:** `correct_changes()` built its `automated.csv` temp-file path via `paste(DIR, "automated.csv", sep = "\\")` — a hardcoded Windows-style separator, malformed on Linux/Mac (a literal backslash has no path-separator meaning on Unix). Confirmed this specific value is only ever written to, never read back, in either OS branch, so the practical impact was a stray oddly-named leftover temp file, not a crash — still fixed, via `file.path()` (which resolves identically to `\\` on Windows for the same real file, so the non-Linux/Shiny hand-off is unaffected).
- **Bug #36:** `differences <- automated != as.matrix(changes)` — when one side is `NA` and the other has a real value (e.g. a user fills in a previously-empty "to_" alternative), `!=` against `NA` produces `NA`, not `TRUE`; `any()`/`which()` only select `TRUE`, so the change is silently treated as "no difference detected." Confirmed directly: correcting a `NA` "to_" cell is discarded entirely, taking the "No responses changed" early return and handing back the original, unmodified object. Fixed by treating a mismatched NA-ness between the two sides as a real difference in its own right.

Merges `textcleaner.fluency()`/`textcleaner.free()` into one `textcleaner()` with internal `type` branches, per binding decision #2 — kept unchanged in name per binding decision #7. Unlike earlier merges, most of the two originals' shared scaffolding had already been factored out into type-dispatching helpers across Phases 2-6 (`obtain_id()`, `convert_miss()`, `prep_spellcheck_dictionary()`, `spellcheck_dictionary()`, `correspondence_matrix()`, `correct_changes()`); what remained genuinely new here was `partBY` transposition, the `keepLength`/`keepCue` filtering mechanics, the `continue` resume-vs-completed dispatch, wiring the pieces together, and the final type-specific reshape (a binary vocabulary matrix for fluency via `responses_to_binary()`, a response x cue frequency matrix for free). `correct_data()`/`correct_data_free()` stay separate per binding decision #2's carve-out. **This was, by a wide margin, the highest-yield phase in the rebuild for genuinely new bugs — 9 newly numbered (#54-62), plus closing bug #10's pattern at a second call site.** Every prior phase's own functions had already been unit-tested in isolation; this was the first time they were all wired together and driven end to end, and integration surfaced defects none of those isolated tests could have caught. Two, bugs #59 and #60, are severe enough that the manual spell-check review step was effectively non-functional for fluency data in specific, entirely ordinary circumstances (see below) — this is very likely the most impactful finding of the whole rebuild so far.

**Two bugs in `textcleaner()`'s own new code, both severe and immediately reachable:**

- **Bug #54:** `partBY`'s own default, `c("row", "col")`, was never resolved with `match.arg()`. Confirmed directly against the installed R version (4.6.1) that `textcleaner(data, type = "fluency")` — the DEFAULT call path, with no explicit `partBY =` — crashes outright ("the condition has length > 1"). Every one of the function's own doc examples happens to always pass `partBY` explicitly, almost certainly why this was never caught in the untouched original either.
- **Bug #55:** the fluency `keepLength` filter had two independent, compounding bugs. Fixing only the word-count mechanism (`length()` always measuring 1 for a single-string cell, regardless of word count) exposes a second, previously-masked off-by-one in the removal threshold (`>= keepLength` instead of `> keepLength`) — `keepLength = 1` would otherwise remove EVERY response instead of just multi-word ones. Confirmed unreachable in the untouched original for any `keepLength` a user would plausibly set, since bug (1) alone masked bug (2) completely.

**Two integration bugs, found only once already-committed Phase 3/4 code was exercised through its actual real calling convention for the first time:**

- **Bug #56:** `obtain_id()`'s own bug #50 fix (`vapply(data, function(x){length(unique(x))}, integer(1))`) silently assumed a data frame — but `textcleaner()` (its only real caller, in both the untouched original and this rebuild) always passes a raw matrix. `vapply()` on a matrix iterates per ELEMENT, not per column, silently defeating the "single all-unique column is the ID" heuristic entirely. `obtain_id()`'s own test suite never caught this because every existing test used a data frame directly.
- **Bug #58:** `resolve_auto_spellcheck_stage()`'s "everything resolved" branch computed `$auto` from only the current stage's remaining candidates, silently dropping every response an EARLIER stage had already resolved — confirmed with `c("dogg", "cat", "bird")` against the animals dictionary, where "cat"/"bird" resolve at the very first stage and only "dogg" needs individual checking: the old code returned `auto = 1` instead of `1:3`. `auto_spellcheck()`'s own tests never exercised this "partial-then-full resolution" sequencing.

**The most severe finding, a compounding pair (bugs #59/#60) that together made the manual-changes review step silently inert for fluency data:**

- **Bug #59:** `res$spellcheck$automated <- corr_mat[spell_check$auto, ]` (no `drop = FALSE`) collapses to a plain vector whenever exactly one response needs automated-change review — an entirely ordinary occurrence, not an edge case. The vector's own `names()` are the correspondence matrix's COLUMN names, not its row name, which is lost outright. `correct_changes()`'s existing `is.vector(automated)` reconstruction (`t(as.matrix(automated))`) restores matrix-ness but has no way to recover that lost row identity. `correspondence[row.names(res$spellcheck$automated), ] <- changes` then silently assigns to zero rows (`row.names()` on the collapsed vector is `NULL`) — a user's spreadsheet edit vanishes with no error at all. Confirmed inherited byte-identically from the untouched original.
- **Bug #60:** even with #59 fixed so the edit lands correctly in `res$spellcheck$correspondence`, the untouched original's fluency branch never re-synced its local `corr.mat` from it afterward — only the free-association branch does. `correct_data()` uses the stale local variable, so the edit still never reached `$responses$clean`/`$responses$binary`. Both confirmed together via one direct reproduction: a "dogg" -> "zebra" spreadsheet edit correctly appeared in `$spellcheck$correspondence` but the untouched original's final cleaned/binary output still showed "dog".

Fixed #59 at the source (`drop = FALSE` when constructing `$spellcheck$automated`/`$manual`) plus defense in depth inside `correct_changes()` (recovering row identity by matching on the correspondence matrix's unique "from" value, for any other caller that might still pass a collapsed vector). Fixed #60 by re-syncing `corr_mat` for both types after `correct_changes()`, not just free.

**One narrower, free-only correctness bug (#61)** in the "mark embedded bad words" correspondence-matrix step: a bare substring match (`grep("NA", x)`) meant to catch a compound response like `"polar NA"` also fires on any ordinary word merely containing "NA" (e.g. `"CANADA"`), only reachable with `lowercase = FALSE`. Fixed with a word-boundary-aware regex, also simplified from a branching `apply()`/`lapply()` pair into one vectorized `ifelse()`/`grepl()` call.

**`convert2snafu()` (bug #62, plus its already-known easycsv dependency, binding decision #5):** the single-dataset branch (`if(length(data.list) == 1){}else{...}`) was completely empty, so the function's own documented single-argument example silently produced an empty CSV — confirmed the `else` branch's group-name derivation works fine for one dataset too, so the special case was simply unnecessary; merged into one path. `easycsv::choose_dir()` replaced with an explicit `path =` argument; the interactive filename prompt rebuilt on `read_input()`/a `reader = readline` parameter per binding decision #3; `1:length(data.list)`/`1:nrow(target.data)` audited and converted to `seq_along()`/`seq_len()` (bug #8 class, zero-dataset/zero-row inputs).

**`continue` resume-vs-completed dispatch (closes bug #10's pattern at a second call site):** the untouched original distinguished "still resuming" from "already completed" `continue` shapes by counting list elements (`length(continue) != 7` for fluency, `> 8` for free) — the identical fragile pattern bug #10 already named, just one level up from where Phase 4 fixed it. Both `continue` shapes already carry an explicit `$stop` flag (`TRUE` mid-wizard, `FALSE` once finished) — routing on that instead is unambiguous regardless of which optional fields happen to be present.

**`edit_fn` added as a new `textcleaner()` parameter** (defaulting to real `edit`), threaded through to `correct_changes()` — needed the moment `textcleaner()` became the first real caller of the rebuilt `correct_changes()` (Phase 6), which already had this parameter but nothing had exercised it end to end. Without it, any `textcleaner()` call reaching the automated-changes review step in a non-interactive context would try to open a real interactive spreadsheet editor.

**Verified:** the fluency data-prep pipeline (`obtain_id()` -> `convert_miss()` -> `prep_spellcheck_dictionary()` -> `uniq_resp` derivation) checked against the real, full-scale `open.animals` raw dataset (516 participants): correctly identifies the real named "ID" column (IDs matching `open.preprocess`'s own row names, e.g. "4", "6", "7", "9"...) and derives exactly 829 unique responses — matching `open.preprocess$spellcheck$correspondence`'s real row count precisely. ## Phase 10 — `best_guess()` spell-correction enhancements

(Phase 9, the Shiny `automated_edit()` rebuild, is tracked separately in
`SHINY_PLAN.md` -- see the closing note on bug #11 above. Phase 10 picks the
`REFACTOR_PLAN.md` numbering back up since it's a direct enhancement to
already-reviewed console code, not a new tracking document of its own.)

Research pass (Norvig's noisy-channel model, SymSpell, phonetic algorithms,
`hunspell_suggest()`) into whether `best_guess()`'s hand-rolled
Damerau-Levenshtein + QWERTY-tiebreak algorithm could be improved by
established practice. Conclusion: the core design -- conservative
edit-distance threshold, give up to manual review rather than guess wrong --
is well-suited to this domain (short tokens against small-to-medium closed
vocabularies, where reproducibility matters as much as accuracy) and should
not be replaced. Two additive enhancements were evaluated; one was
implemented, one was built, honestly benchmarked, and rejected.

**Phonetic (Metaphone) disambiguation, added.** A real blind spot confirmed
directly: `best_guess("graple", full_dictionary = coca.dictionary)` gave up
ambiguously between `"grape"`/`"grapple"`, since `qwerty_distance()` requires
same-length words and both candidates differ in length from the input --
`phonics::metaphone()` resolves this instantly (`"graple"`/`"grapple"` both
code to `"KRPL"`, `"grape"` codes to `"KRP"`, different). Added
`get_phonetic_code()`/`phonetic_match()` (`R/helpers.R`, memoized, matching
`get_dictionary_hash()`'s established cache pattern) and a new disambiguation
branch in `best_guess()`'s ambiguous-tie path, confined to the same
tolerance-eligible candidate set `qwerty_distance()` already operates on.
QWERTY and phonetic are evaluated as peers, neither trusted over the other:
agreement reinforces the answer, disagreement falls through to manual review
rather than arbitrarily picking one -- confirmed via direct adversarial
testing that a `"gremble"` typo of `"grumble"` has QWERTY's adjacent-key
logic pick `"tremble"` while Metaphone correctly picks `"grumble"`, two
independent heuristics with no principled reason one should always outrank
the other. A follow-up design question -- computing edit distance over the
Metaphone codes themselves, rather than requiring exact equality, for a
looser match -- was verified and rejected: a distance-≤1 threshold on the
codes reintroduces exactly the ambiguity exact-match was added to resolve
(`"grape"`/`"grapple"`'s codes, and `"grumble"`/`"tremble"`'s codes, are each
DL-distance 1 apart). `hunspell` and `phonics` (both reachable from
`textcleaner()`'s own default pipeline, via `word_is_recognized()` and this
new branch respectively) promoted from `Suggests` to `Imports`, per direct
request -- their `requireNamespace()` guards removed accordingly.
`@references` gains a Philips (1990) Metaphone citation alongside the
existing Damerau (1964) one.

**SymSpell-style precomputed-deletion index, built, benchmarked, rejected.**
A symmetric-delete index (`build_symspell_index()`) was fully implemented,
including two real vectorization fixes found along the way (grouping
same-length words for one vectorized deletion-variant generation per
`(length, k, combination)` triple instead of a per-word loop; `unique()` +
`match()` + integer-keyed `split()` instead of `split()`'s own internal
`factor()`/sort over millions of string keys) and its correctness guarantee
verified empirically (446 randomized mixed-edit trials against
`coca.dictionary`, 0 misses). A real microbenchmark with a pre-warmed cache
(the honest number, not the ~400x-inflated one an initial flawed timing loop
that included a cold-cache index rebuild inside the timed calls produced)
showed brute-force `stringdist()` at ~6.0ms/call vs. the SymSpell fast path
at ~2.5ms/call -- a real ~2.4x per-call speedup, but against a ~39s one-time
index-build cost, implying a breakeven of roughly 11,000 `best_guess()`
calls against the same dictionary in one session. Not realistic for any real
`textcleaner()` run. Rejected as not worth the added complexity, per direct
decision.

**Verified:** full `devtools::test()` re-run after the phonetic-disambiguation
change: 721 tests passing, 0 failures (6 pre-existing warnings, all the same
`'package:SemNetCleaner' may not be available when loading` `future.apply`
artifact already documented at Phase 4/8, unrelated to this phase).
`devtools::check(cran = FALSE)`: 0 errors, 0 warnings, 0 notes.
